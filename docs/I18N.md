# Localization - 1.0.0

## Languages and catalogs

The app supports `en`, `ru`, `es`, `pt-BR`, `de`, `fr` and `pl`.
`locales/<code>.json` is the single source of translated UI and HTTP error messages.
English is the per-key fallback. Task text, technical identifiers and product names
are never translated. Language options use native names, without country flags.

`frontend/src/i18n.mjs` owns normalization, resolution, formatting and error
recognition. `Intl.NumberFormat` and `Intl.DateTimeFormat` use each catalog's BCP 47
locale. UI dates use the browser/system time zone. Error bounds on the Python side
are integer values with language-appropriate grouping. Pydantic diagnostics are
presented as localized validation messages while retaining strict types and HTTP 422.

To add a language, add its JSON catalog, import it into the frontend registry and
rebuild. The picker and resolver use that registry; Python discovers the shared
catalog files automatically. Tests check complete key coverage and interpolation
parameters. A temporarily missing translation still falls back to English.

## Resolution and persistence

1. A valid manual app choice in `ptm.language` wins.
2. Otherwise use the active Hermes locale exposed by the SDK.
3. If that SDK locale is unavailable, consult `navigator.languages` in order.
4. Use English when no supported language can be resolved.

Regional variants match the supported language family, including `pt` -> `pt-BR`.
An unsupported explicit Hermes locale resolves to English, rather than silently
choosing an unrelated browser language. The Automatic option clears the app
choice without changing Hermes settings. Existing `en`/`ru` preferences are kept
as manual choices; an absent or invalid preference means Automatic.

The compact gear menu contains the picker and the current language source.
Changes are immediate. Browser `languagechange` and `storage` events are observed,
and cached profile controllers synchronize their preference when reactivated.
Draft text, revisions, focus and confirmations survive language changes.
Messages that arrive in the previous language are recognized by their catalog key
and displayed in the current language. Unknown host errors receive a localized
generic message instead of leaking untranslated diagnostics.

## Hermes integration: verified public contracts

Both integrations use the public `useI18n().locale` hook, never a guessed config
endpoint, private storage key or DOM language scrape. Source reference revision:
`f7e2898aaefc8f967dbf7345e3999a65672fe60e`.

- [Dashboard SDK documentation](https://github.com/NousResearch/hermes-agent/blob/f7e2898aaefc8f967dbf7345e3999a65672fe60e/website/docs/user-guide/features/extending-the-dashboard.md)
- [Dashboard hook implementation](https://github.com/NousResearch/hermes-agent/blob/f7e2898aaefc8f967dbf7345e3999a65672fe60e/web/src/i18n/context.tsx)
- [Desktop SDK exports](https://github.com/NousResearch/hermes-agent/blob/f7e2898aaefc8f967dbf7345e3999a65672fe60e/apps/desktop/src/sdk/index.ts)
- [Desktop/WebApp hook implementation](https://github.com/NousResearch/hermes-agent/blob/f7e2898aaefc8f967dbf7345e3999a65672fe60e/apps/desktop/src/i18n/context.tsx)

Dashboard exposes `SDK.useI18n`; WebApp imports it from `@hermes/plugin-sdk`.
Both return a reactive context with `locale`. Desktop's loading/config-error state
falls back to the browser until Hermes has a usable locale. The app does not call
Hermes's `setLocale`, write `display.language`, install language packs or change
host language settings. Product metadata such as the host's static plugin name
is not translated by the app picker.

On older hosts lacking the hook, browser/system fallback is intentional. External
edits to Hermes configuration are reflected when Hermes itself updates its locale
context. If browser storage is blocked, manual switching still works for that
loaded page, but persistence across sessions cannot be guaranteed.

## Verification

- `npm run build` and `npm test` passed.
- All seven catalogs, placeholders, regional normalization, missing-key English
  fallback, manual persistence, live Hermes inheritance and storage failure passed.
- Actual Dashboard and WebApp adapter modules were mounted against fixtures using
  the documented SDK contract. Tests cover live inheritance for all seven languages,
  manual override/reset, language changes during dirty drafts, focus, revisions,
  cross-tab storage synchronization and browser fallback.
- Python suite in the existing `.local/reorg-venv` passed all 41 tests, including
  FastAPI, language-specific HTTP 409/422 errors, unchanged validation rules,
  concurrency, completion, Trash and restoration. The test framework emits one
  dependency deprecation warning; tests pass.
- Chromium checked 28 combinations: seven languages x two adapters x actual
  1200/360 px viewports. Settings, action menus, confirmations, native required-field
  messages, live switching, dates, close icon alignment and horizontal overflow
  were checked with synthetic data; screenshots were visually inspected.

Run the browser check with:

```text
python scripts/check_i18n_layout.py --chromium /path/to/chrome
```

It uses Node's built-in WebSocket for Chromium DevTools viewport emulation and
requires the existing npm development dependencies. Results and screenshots go
to `.local/i18n-layout/`. No authenticated Hermes sessions or task databases are
used by these browser fixtures. This verifies the SDK contract and both adapter
modules; a live-host/physical-phone acceptance check remains separate.

Version 1.0.0 includes this localization. Release preparation validates a separate
candidate; updating the working VPS is a separate rollout. No task schema or business rules were changed.
